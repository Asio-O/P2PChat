# Agent Note: Making /connect bidirectional — the listen endpoint can only be self-reported by the initiator

Status: implemented

## Problem

`/connect <ip:port>` used to be **one-directional**: A learned B's NodeId and endpoint, so B's public key and identity ended up on A's side; but **B knew who A was and not where A was**. The typical symptom is "on one LAN, one machine can reach the public internet and the other cannot, and the one that cannot can never look the other up" — because it has neither the peer's endpoint nor a DHT result for it.

The first fix direction was: on the responding side, read the peer address from `senderConnection.RemoteEndPoint` and write it into the static peer table. **That direction is wrong**, and wrong in a very specific way: `RemoteEndPoint` is the **source endpoint of that outbound connection**, whose local port is dynamically assigned by the kernel from the ephemeral range and has nothing to do with the node's actual TCP listening port. Registering an ephemeral port as "where the peer is" guarantees that any call-back is refused. Worse, `FindNodeAsync` gives static peers **priority** (`MainlineDhtService.cs:243`), so a bogus "peer IP:ephemeral-port" record does not merely fail to connect — it **permanently shadows** that peer's DHT resolution path, escalating "can't connect" into "can never be resolved again".

The root cause is not an implementation oversight but the protocol itself: **the three-way handshake carries only source IP and source port, never the peer's listening port.** On the responding side that information simply does not exist at the protocol layer — only the initiator can say it.

## Decision

**Let the initiator self-report its listening endpoint in the hello payload**, and have the responder use that for the reverse registration:

- A new `KeyExchangeMessage.SenderListenEndPoint` (`[Key(12)]`, `string?`). It sits inside the **Payload that the signature covers as a whole**, so "A claims it listens on P" is **attributable**: changing one character breaks verification. It is filled from `IDhtService.LocalNode.EndPoint` — the local LAN IP plus TCP listening port.
- The property deliberately uses `init` with **no initializer**, for the same reason documented on `Message.MessageId`: `init` plus an initializer gets unconditionally reset to `default` by MsgPack during deserialization; with no initializer, a **missing key means no assignment and it stays null** — which is exactly the degradation semantics needed for "an older peer does not carry this field".
- The responder's `KeyExchangeHandler.RegisterInboundPeer` **prefers the self-reported endpoint**; when the field is missing (older peer) or `EndpointText` fails to parse, it **degrades**: it records the identity and public key in `PeerPublicKeyRegistry` and **does not write the static peer table**.
- The degradation branch does **not** "just assign null to the endpoint" — `NodeInfo.EndPoint` is `required` (`NodeInfo.cs:51`), so that option does not exist at the model layer. The static peer table means "I know **where** it is", and the current model cannot express an entry whose identity is known but whose endpoint is not. Allowing that would first require making `EndPoint` nullable, a model change that reaches every one of `FindNodeAsync`, the connection pool, and group fan-out. Stating that cost clearly is what stops the next person from thinking it was merely a forgotten line.
- **Identity comes from the envelope, uniformly**: when crossing `MessageRouter` dispatch, the payload's `SenderId` must equal the envelope's `SenderId`; the handler itself takes identity solely through `TrySenderNodeId(envelope)` and **deliberately offers no "fall back to the payload" path**.
- A pre-registration self-check: when the public key and identity are not self-consistent (`publicKeyBound == false`) it **does not register** — at that point the `NodeId` and the public key disagree, and writing that into the static peer table is a poisoned record. A failure to register also must not break the key exchange itself (the session key already exists by then), but it must leave a trace, or the user only sees "it can't reach me" with not one line in the log.

## Alternatives considered

**Register the static peer from `senderConnection.RemoteEndPoint`** (the original approach). Rejected, and the root cause deserves to be stated all the way down: **the listening-port information does not exist on the responding side at all.** The three-way handshake does not carry the peer's listening port; `RemoteEndPoint` gives the **kernel-assigned ephemeral port of this connection**, semantically unrelated to "where that node normally listens". This is not an implementation oversight — the protocol layer has no such information. On top of that there is a second cost: static peers take priority over DHT resolution, so a bogus record does not just fail to connect, it **permanently shadows** every future discovery path for that peer. **This is the lesson this record most wants to leave behind: a field that is syntactically valid, compiles cleanly, and yet points at something else entirely is more dangerous than an obviously wrong field.**

**Make `NodeInfo.EndPoint` nullable so the static peer table can hold "identity known, endpoint unknown" entries.** Rejected: not in this round. That is a model-layer change reaching `FindNodeAsync`'s resolution order, the connection pool's key design, and the reachability judgement for every member of a group fan-out — not something to slip in casually. Degrading to `PeerPublicKeyRegistry` expresses the same thing with zero risk.

**Use contacts from `contacts.json` as the endpoint / identity binding.** Rejected: that is the user's *intent*, not "an identity we verified with our own eyes". Treating a hand-written NodeId + ip:port as a verified binding promotes an out-of-band human assertion into a system-level security assertion — a user's typo becomes an input to security policy.

## Consequences

- `/connect` goes from one-directional to bidirectional: after one `/connect`, B can also find A, and **the initiator no longer has to `/add` or issue a reverse `/connect`**. The "one machine on the LAN can reach the internet, the other cannot" scenario becomes viable.
- **Cost: the self-reported endpoint is only correct within the same LAN.** The sender fills in its **LAN IP plus listening port**, which is **unreachable for a peer across NAT** (a private IP means nothing once it leaves the NAT). Cross-NAT scenarios rely on DHT resolution for the public endpoint and do not go through the `/connect` reverse registration, so they are unaffected — but this applicability boundary must live in the code comment, or the next person will assume it is a general-purpose mechanism.
- **Cost: older peers cannot use the reverse path.** An old node that lacks the field takes the degradation branch: B records A's identity and public key but **does not write the static peer table**, so A still cannot call back. The degradation is explicit (a `LogInformation` explains why and points at `PeerPublicKeyRegistry`) rather than silent — but the user's experience is still "it can't reach me".
- **Reverse reachability is a by-product of the peer consenting to be found.** B knows where A is because A said so in the hello; that is an attributable *claim*, not something B verified independently.
- The new `[Key(12)]` is a wire field addition, but MessagePack's key-as-array-index semantics guarantee that **inserting a key does not shift existing ones**, so it stays compatible with the existing format.

## Comment discipline

This round ran into the same family of problem once more: **a guarantee claimed by a comment must actually exist on the current code path.** It is the third occurrence in this same patch of code, which is why it gets its own section instead of being treated as a one-off.

### This family spans three carriers, not just code comments

What this record kept running into is the **same mistake across three carriers**: **a narrower piece of evidence being written up as a broader conclusion.** It does not only happen in code comments:

- **Test side.** The e2e assertions A30/A31 claimed to verify "the plaintext appears on the receiver", and the evidence that satisfied them was the single line `私聊消息已处理: {Sender} -> {Text}` at `PrivateMessageHandler.cs:102` — **that log line itself contains the plaintext.** So the assertion was satisfied by a log line and passed, while never verifying "the user actually saw it". The `PASS=39 / FAIL=0` recorded that round was, for "display", a quiet false green.
- **Documentation side.** The XML comment on `ReadHelloResponseAsync` claimed "VerifyEnvelopeCore already enforces public-key ↔ identity binding", yet that path **never invoked** that function — the claim's strength exceeded what the code actually backed.
- **Note side.** While writing this record, a relayed claim that "`EvaluatePeerIdentity`'s 'prefer rejection' branch is dead code" was tested against the code and **did not hold**. Had it been written in anyway, it would have become the next generation's "settled fact".

**So the warning applies to Notes / Tests / Docs three layers alike**: before writing any assertion, ask "how broad a conclusion does the evidence I actually have support?" — almost always narrower than the sentence itself. This family already has a name in `HANDOFF.md` §7.3(b) and §7.4: §7.3(b) is "writing a narrower / uncertain evidence as a broader conclusion", §7.4 is "the green light points at code that was never compiled" — both are the same family as the three listed above.

**This record itself is a product of that discipline.** Another team member, while executing a different task, found that a salvage commit had already landed their output, so what they did was "validate line by line" rather than "rewrite" — this is the same discipline as "the formal gate must start with `dotnet build -t/Rebuild`": **when an unexpectedly good result shows up, suspect your measurement before accepting it.** That particular false green had this shape: the code actually contained a `CS0165` compilation error, the incremental build nevertheless reported 0 errors / 0 warnings, the full gate ran 375 tests green — both rails failing simultaneously. Without `-t/Rebuild`, this record would likely have been written against wrong code. See `HANDOFF.md` §7.4 and `Agent.md` "the formal gate must start with `dotnet build -t/Rebuild`".

**Instance one (a historical one, since fixed).** `KeyExchangeHandler.HandleAsync` used to contain a self-contradiction: **six lines apart**, one place took the peer's identity from the payload's `SenderId` and another from the envelope's. Both look right, but only the second is trustworthy — `SenderId` inside the payload is fully controlled by the peer. This is not a hygiene issue: that value is the **key** for `SetSessionKey`, and getting it wrong does not raise an error — it means every subsequent private chat to that peer looks up an empty session slot, packets go out, the peer receives them, the UI stays empty, and the scene is almost evidence-free. The code comment now records it (`KeyExchangeHandler.cs:144`: "historically this method contained a 'six lines apart, one trusting the payload and one the envelope' self-contradiction; fixed").

**Instance two (still present today).** The XML comment on `RegisterInboundPeer` lists four items as "security constraints (kept for whoever implements this later — not one may be skipped)", and the fourth is "**must not overwrite an existing entry**: a registered endpoint may be more trustworthy than a newly observed one". But the call site contains no such check, and `MainlineDhtService.RegisterStaticPeer` is an **unconditional overwrite** (`_staticPeers[node.NodeId.ToHexString()] = node;`). In other words this constraint, the one declared "not one may be skipped", **does not hold on the current code path**. Implementing it properly means adding a "skip if already present" in `RegisterStaticPeer` or an explicit existence check before the call in `RegisterInboundPeer` — not leaving it in a comment. Because the comment says "not one may be skipped", a reader will assume it has already been implemented.

**A methodological lesson attached to this.** While writing this record, someone relayed that "the 'prefer rejection' branch of `EvaluatePeerIdentity` is dead code". Checking against the code, the assertion does not hold: that code **does** implement no-early-return and conflict-beats-match, and a dedicated case — `端点身份判定_同一端点换了身份必须判为冲突_这是唯一能拒自签攻击者的手段` — exercises it. It was therefore *not* written into this record as a second instance of comment/code mismatch. **An assertion that was never checked, once it lands in a permanent archive, becomes the next generation's "settled fact" — the same harm as a wrong comment, only by a different route.**

## Testing

`tests/P2PChat.Chat.Tests/KeyExchangeIdentityTests.cs` (391 lines, **7 cases**) locks down this decision. **The case names are themselves a summary of the assertion** — this is a deliberate convention in the project, so the test list alone tells the reader what each one defends, without having to open the file:

- `载荷SenderId与信封不一致时_第三方不得获得任何东西` — when the payload impersonates a third party, the third party **gets neither the session key nor the static peer registration**. 8 assertions.
- `正常对端_会话密钥与静态对端登记都必须来自信封与自报监听端点` — happy path: the session key and the static peer's endpoint **both** come from the envelope and the self-reported field. 9 assertions. **This includes the round's key negative-assertion**: a connection is built with source port `42002`, then `registered.EndPoint.ShouldNotBe(connection.RemoteEndPoint)` is asserted. It is **negative** — not "the endpoint equals X", but "the endpoint **is not** that outbound connection's source port". A positive assertion can only prove "some endpoint was written"; only the negative assertion can precisely catch the specific error of "ephemeral source port was used".
- `对方未自报监听端点时_不写静态对端表_但身份与公钥仍被登记` — degradation semantics: an older peer does not write the static peer table, but the identity and public key **are still** recorded into `PeerPublicKeyRegistry`.
- `正常对端_重复请求不会重复登记同一静态对端_但会话密钥会被刷新` — under a repeated request the session key is refreshed, the static peer registration is not duplicated.
- `载荷与信封不一致时_拒绝理由里必须点到SenderId这个稳定token` — the rejection reason must contain a **stable token** (`SenderId`), not the full sentence (which would change with log wording and let the assertion quietly fail).
- `密钥交换响应不得登记静态对端也不得写会话密钥` — the response direction produces no registration.
- `公钥与身份不自洽时_即使直接调用处理器也不得登记静态对端` — bypassing the router and **calling the handler directly** still has the binding re-checked by the handler itself.

Two of them — "payload vs envelope mismatch" and "negative-assertion for happy path" — have been **proved non-vacuous via mutation**: flipping the assertions to their opposites makes them red, so they actually test something rather than being always-true. All cases enter the handler through the real `MessageRouter`.

## Deferred

- `NodeInfo.EndPoint` is still `required`, so the static peer table cannot express "identity known, endpoint unknown"; degraded entries currently live in `PeerPublicKeyRegistry`. If such peers are ever to be reachable via `/msg`, that model change has to come first.
- **The "must not overwrite an existing static peer entry" constraint has not been implemented yet** (see `## Comment discipline` instance two): `MainlineDhtService.RegisterStaticPeer` is still an unconditional overwrite. **This record only characterizes the problem; the fix is for next round.** The product decision taken is **hand-registered wins on conflict**: a hand-registered entry is a one-off, conscious act by the local user via the console, unreachable by an attacker; a self-reported endpoint is the peer's claim inside a signature-covered payload — the signature only guarantees "this peer said it", **it cannot tell whether the peer lied**. So the self-reported endpoint is weaker on the attack surface. The implementation lands in `RegisterStaticPeer`: "if an entry already exists and its endpoint differs from the new one ⇒ keep the old endpoint, log a `LogWarning` recording the difference and its source"; the self-reported-endpoint path goes through this revised entry point.
- The bidirectional `/connect` path now **has end-to-end proof** (`scripts/e2e-verify.ps1` **A35**, see commit `189190b`): nodeB2 `/connect` nodeA2 → A2 reverse-registers from B2's self-reported endpoint → A2 `/add` B2 (no endpoint) → A2 `/msg` → B2 receives. **Still NOT covered by e2e**: the "must not overwrite an existing static peer entry" constraint (see instance two), and the cross-NAT case (where the self-reported endpoint is a private IP and is unreachable by design).
