# Agent Note: Inbound replay protection (timestamp freshness window + MessageId dedup)

Status: implemented

## Problem

Phase 3.2 gave every message an ECDSA self-signature, and `SenderId` is now strongly bound to the sender's long-term public key (`NodeId.FromPublicKey(pubkey) == SenderId`). But **a signature only proves "this message was produced by the holder of the corresponding private key"; it does not prove "this is a new message"**. An attacker who records one perfectly valid envelope and replays it repeatedly still passes every signature gate: missing-signature check, sender-public-key ↔ `SenderId` binding, ECDSA verification — none of the four stops it.

The two fields that could have provided a temporal backstop do not (both **verified**):

- `MessageEnvelope.SequenceNumber` is written by `MessageRouter.NextSeq()` (`Interlocked.Increment`) and is covered by the signature, but **nothing anywhere in the repository validates it** — the only place it is read is the `LogTrace` at the end of `SendViaConnectionAsync` (`MessageRouter.cs:125-126`), pure logging.
- `MessageEnvelope.Timestamp` is covered by the signature but is **never compared against the current time** — every read site (each handler's `FromUnixTimeMilliseconds`, the TUI's `ToLocalTime()` for display) merely restores it into a time for display or persistence. No freshness decision exists.

What is left defends only "the message really came from that private-key holder". Nobody is responsible for "is this message appearing for the first time right now".

## Decision

A **stateful, non-cryptographic** inbound admission step is added, sitting beside signature verification but not as a fifth signature gate. The contract lives at the root of the dependency graph, `P2PChat.Core.Abstractions.IReplayGuard`, with the single method `bool TryAccept(MessageEnvelope envelope, out string? reason)`; the implementation is `P2PChat.Chat/Routing/MessageReplayGuard`. It is invoked in `MessageRouter.RouteIncomingAsync` **after verification passes and before handler dispatch**.

Two layers, coarse and fine:

1. **Timestamp freshness (coarse, catches stale replays)**: `envelope.Timestamp` must fall inside the closed interval `[now - maxAge, now + maxFutureSkew]`. `maxAge` defaults to **1 hour**, `maxFutureSkew` to **5 minutes**. Out of range is a rejection, and `reason` distinguishes "too old" from "from the future". The escape hatch `maxAge <= 0` turns off **the entire** time-window check (`if (IsTimeWindowEnabled && !TryCheckFreshness(...))` at `MessageReplayGuard.cs:102`) — **not merely a relaxation of "too old"**: future-dated timestamps stop being rejected too. A half-open escape hatch is deliberately avoided, because it leaves people believing some time protection remains when it does not; with the hatch open the only surviving defence is the second layer, and that is stated in the wiring warning and in the self-test display.
2. **`MessageId` dedup (fine, catches replays inside the window)**: `MessageId` is a 16-byte Guid, **covered by the signature**, generated per message by `Message.NewGuid()` (`Message.cs:26`, `set` rather than `init` so deserialization does not reset it). Recently accepted `MessageId`s are kept **bucketed by peer NodeId** (default **1024** per bucket); a repeat is rejected. The cache is **bounded**: buckets are fixed-length ring buffers, and the "peer → bucket" dictionary itself is capped at `MaxTrackedPeers = 512` with LRU eviction, for a worst case of `512 × 1024 × 16B = 8 MiB`. Bounding the peer count too is deliberate: only peers that **pass verification** (i.e. that hold a valid private key) ever allocate a bucket, so the attack surface is already tiny — but until the dictionary is capped as well, the whole structure cannot honestly be called bounded.

Verdict details: `MessageId == Guid.Empty` is rejected outright ("no usable replay dedup key"), because an envelope without a replay key disables the second layer entirely; the per-peer bucket key is the lowercase hex of `SenderId`, degrading to `"malformed:<len>"` when `SenderId` has an abnormal length so that malformed data is never used to build a dictionary key. The time window is a **closed interval** `[now - maxAge, now + maxFutureSkew]`: a boundary value represents "exactly at the limit", a legitimate case that should not be killed, and an attacker pinning the timestamp to the boundary gains nothing — they cannot move `Timestamp` across the boundary without breaking the signature, and a timestamp inside the window still has to pass the dedup layer.

The interface contract explicitly demands **thread safety, and atomicity of the verdict for a given envelope** — when two identical envelopes arrive concurrently, exactly one may return true, otherwise concurrent replay would slip through. The implementation gives each bucket a lock and performs the "duplicate check + ring write" inside **one critical section**; split into `Contains` and `Add`, two concurrent copies of the same envelope would both pass.

`MessageRouter`'s constructor takes a **required** `IReplayGuard` parameter with no default: an optional parameter (`IReplayGuard? x = null`) would make "forgot to inject" silently equal "protection disabled", which is a security trap. The call site sits in `RouteIncomingAsync` after `VerifyEnvelope` and before `_handlers.TryGetValue` — **after verification** so that no work is wasted on attacker-controlled data, and **before dispatch** so that a replayed message can have no side effects at all. On rejection `IReplayGuard` logs one `LogWarning` carrying the explicit reason (too old / from the future / duplicate), and `MessageRouter` adds only a `LogTrace`, so the same event does not appear twice in the log. The clock is injected as `Func<DateTimeOffset>? now = null` (defaulting to `() => DateTimeOffset.UtcNow`) so tests can supply a fixed clock instead of sleeping.

Wiring and visibility: the config item `P2PChat:ReplayMaxAgeSeconds` (`double`, default `3600`, `<= 0` disables the time window) is parsed in `Program.cs`, converted to a `TimeSpan` and injected into `IReplayGuard`; when disabled it logs a `LogWarning` rather than failing silently. In DI order `IReplayGuard` must come before `IMessageRouter` (the latter's parameter is required), and `ChatServiceCollectionExtensions` additionally provides a `TryAddSingleton` registration carrying the defaults. The TUI does not ask `IReplayGuard` (that is a security boundary exposing only `TryAccept`); instead the wiring injects an immutable `ReplayGuardStatus` value record, and the self-test block prints a `重放防护:   …` line — a downgrade must be visible, not silent.

## Alternatives considered

**A per-peer `SequenceNumber` high-water mark — reject anything below the watermark.** Rejected, and rejected for concrete mechanisms rather than for being "unsuitable":

- **It resets to zero on process restart.** `SequenceNumber` comes from `MessageRouter._seqCounter`, an **in-process** counter (`NextSeq() => Interlocked.Increment(ref _seqCounter)`), and is never persisted. A peer that restarts begins again at 1 while we still hold the watermark accumulated before its restart — so **every single message that peer sends after restarting falls below the watermark and is rejected wholesale**. This is not theoretical: restarts, crash recovery and reconnect-after-network-change are routine.
- **A single node has two independent sequence counters.** Besides `MessageRouter._seqCounter`, `KeyExchangeHandler` keeps its own `_responseSequence` (`KeyExchangeHandler.cs:225`); both start at 1. That means **different messages from the same peer can legitimately carry the same `SequenceNumber`** — the sequence number is simply not a unique key in this protocol, and any dedup built on it will read legitimate duplicates as replays.
- **Frames from one peer arrive out of order under concurrent delivery.** "Below the watermark ⇒ reject" then kills late-but-perfectly-legitimate frames, and that false rejection is indistinguishable from a real replay in the field.

The root cause is that a sequence window requires sequence numbers to be globally monotonic and gap-free across restarts and across code paths. This protocol has no such guarantee.

**Fold the policy into `MessageRouter.VerifyEnvelope`.** Rejected: `VerifyEnvelope` is **purely cryptographic**, stateless and re-callable, and `MessageSigningTests` invokes it directly in 9 places. Stuffing a stateful policy inside it corrupts its semantics — **verifying the same envelope twice would make the second call fail**. That is not "stricter", it is turning a pure function into a side-effecting one. And it would blow up a batch of cryptographically correct tests, burying the real failures in noise. Policy and cryptography must stay separate.

**Time window only, no `MessageId` dedup.** Rejected: a one-hour window does nothing against "record one packet, replay it ten thousand times" — the most economical attack there is — because the attacker only has to replay inside the window.

**`MessageId` dedup only, no time window.** Rejected: dedup is **exact but bounded** — once ring eviction has discarded a `MessageId`, it can be accepted again, and without a time window there is no upper bound on how long that loop can run or how old the replayed frame is. The time window supplies that upper bound: anything past `maxAge` is rejected regardless of cache state.

**Persist the `MessageId` dedup cache to disk.** Rejected: persistence would let "what I have already seen" outlive the process, while a restarted peer must be able to talk normally again. It adds IO and consistency cost and decouples the cache's lifetime from identity/session lifetime. The trade taken is: cross-restart long-range replay is covered by the time window; exact cross-process dedup is not pursued.

## Consequences

- Inbound gains one more admission point: a frame that **passes verification but is judged a replay is rejected before handler dispatch**, so business logic never runs. The reason (too old / from the future / duplicate) is logged at `LogWarning` and is queryable.
- **Cost: clock skew causes false rejections.** When two machines' clocks differ by more than `maxFutureSkew` (default 5 minutes), perfectly normal messages are judged "from the future" and rejected; the default one-hour `maxAge` likewise rejects stale-but-legitimate messages on long-lived connections. This is a **deliberate trade of "rejecting a few stale messages" for "stopping unlimited replay"** — with no freshness check at all, replay is wide open. The escape hatch is `ReplayMaxAgeSeconds <= 0` (turning off **the entire** time-window check — neither too old nor from the future is rejected any more), for machines with badly skewed clocks; turning it off means the time layer is gone, so turning it off must produce an explicit warning rather than living only in a config file.
- **Cost: `MessageId` dedup is bounded.** Only the most recent 1024 per peer are kept, so replays older than the eviction may still pass; the time window only covers the portion still inside the window. The two layers stack; they are not interchangeable substitutes.
- **Cost: rejection is policy-based and orthogonal to cryptographic verification.** A frame rejected by replay protection **is not thereby an invalid signature**, and conversely a frame that passes replay protection still carries a valid signature. Logs and warnings must let a maintainer tell the two apart, or debugging will head in the wrong direction.
- The constructor takes a **required** parameter: forgetting to inject `IReplayGuard` fails at construction instead of silently degrading to "protection off". Every construction site (DI wiring, test harnesses) must be updated in step — that is intentional.
- **Interaction with file transfer was checked**: every `FileChunkMessage` / `FileMetaMessage` is a fresh instance whose `MessageId` comes from `Guid.NewGuid()`, so chunks are never killed by dedup.
- **A hello response is unaffected by how long the peer hung.** `KeyExchangeHandler` sets only four fields explicitly when building the response message (`SenderId` / `ConversationId` / `EphemeralPublicKey` / `IsResponse`, `KeyExchangeHandler.cs:149-156`); `MessageId` and `Timestamp` come from the `Message` base class property initializers (`Message.cs:26`, `:35`), so they are a **fresh Guid and the moment the response was produced**. The freshness verdict therefore targets the response's own production time, so even if a peer hangs for a long time before replying, that response is accepted normally rather than misjudged as too old.
- **Group fan-out is what forces per-peer bucketing.** `GroupChatService.SendGroupMessageAsync` sends the **same `Message` object** — and therefore the same `MessageId` — to every different member of the group (`GroupChatService.cs:222-231`). If the dedup cache were a global set, **the second group message would be dropped network-wide** — and a single-node test cannot catch that at all, because a single-node scenario has no second recipient.

## Testing

`tests/P2PChat.Chat.Tests/ReplayGuardTests.cs` (30 cases: 28 `[Fact]` plus one two-case `[Theory]`) and `tests/P2PChat.Integration.Tests/ReplayProtectionTests.cs` (4 cases, real TCP and real ECDSA signatures) pin this decision down together. `dotnet build P2PChat.slnx` is 0 errors / 0 warnings and `dotnet test` is 331 passing / 0 failing (Crypto 8 / Core 52 / Chat 110 / Integration 138 / Networking 23). Three of the approaches are worth recording, because they are precisely the things neither the contract nor the implementation can prove — only a test can:

- **The closed interval is nailed down with paired construction**: a frame exactly at `now - maxAge` is accepted, a frame exactly at `now + maxFutureSkew` is accepted, one millisecond outside either end is rejected, and a further case checks that both bounds hold on the same guard without drifting due to ordering. If you only test values in the middle of the window, a "closed interval implemented as an open one" deviation is simply undetectable.
- **Concurrency atomicity uses bare `Thread` plus `Barrier`**: 64 threads deliver the same envelope simultaneously and exactly one is asserted to pass; a second case delivers 8 peers × 24 messages × 4 copies — 768 deliveries — asserting each is accepted exactly once. `Task.Run` is **deliberately not used**: `Barrier` blocks its participants, and pushing them all into the thread pool makes the pool expand on a second-scale schedule to compensate, which is both slow and makes injection timing nondeterministic, making the test itself flaky.
- **Cache boundedness is asserted behaviourally, not by inspecting the entry count**: with `historySize = 8`, nine entries are inserted and the assertion is that the oldest is accepted again on redelivery (evicted) while the most recent is still rejected. There is an **ordering trap** here — every "accepted" verdict writes into the ring and pushes out that bucket's oldest slot — so the "still remembered" assertion must come first and the "already evicted" assertion last, otherwise the earlier acceptance evicts the very object under test and produces a false red. Behaviour rather than entry count is asserted because `PeerBucket` is private and exposes no counting accessor.

The four integration cases go through the real path: frames are captured by `NodeHarness.Start`'s **connection decorator** hook at the exact moment the router writes the bytes out, so what is captured is the **real on-the-wire bytes**, and the attacker opens a **second connection** with its own `TcpTransport` and resends them verbatim. Two choices are deliberate: the test **does not re-sign** (re-signing tests "sign again", not "replay"), and it **first asserts that the captured frame passes `VerifyEnvelope`**, so that what is under test is definitely a replay rather than an invalid packet. The other three are controls: five consecutive replays are each blocked and each leaves a "duplicate" warning, consecutive normal messages are all delivered without false positives, and one group message fanned out to two members reaches both (that last one stages the real reason for per-peer bucketing directly).

One detail worth knowing about observability: `MessageRouter` logs only `LogTrace` for a replay rejection (deliberately, to avoid two lines for one event); the real `LogWarning` is logged by `MessageReplayGuard` — so a "the warning is queryable" assertion has to hang off the guard's logger.

All key assertions passed mutation testing: 14 of them were inverted, every one turned red, and all were then restored.

## Deferred

The following residual risks are **not solved** by this implementation (consistent with `Agent.md` §7):

- **A `MessageId` evicted by the ring may still be replayed successfully.** Only 1024 per bucket are remembered; once a peer sends more than 1024 messages inside the time window, the oldest `MessageId`s are pushed out and replaying them is caught only by the first layer, the time window.
- **After a peer bucket is LRU-evicted, that peer's dedup protection is immediately gone.** Past 512 distinct peers the least recently used bucket is dropped, and replaying the messages that peer recently sent is no longer caught by the second layer — again only the time window backstops it (a `LogWarning` is emitted at eviction).
- **With `ReplayMaxAgeSeconds <= 0` only the `MessageId` dedup layer remains.** Both halves of the time window are off, and combined with the two items above, an evicted `MessageId` can be replayed repeatedly. An attacker **cannot forge a new `MessageId`** — it is covered by the signature, and altering it fails verification — so what remains is "replaying old ids", not "injecting new ones".
- **Dedup state is purely in memory and is lost on process restart.** Replaying an envelope received before startup is not caught by the second layer; only the time window backstops it.
- **It does not stop traffic redirection or denial of service.** It only decides "may this message enter the handler"; it says nothing about link-layer or network-layer attacks.
- Cross-restart long-range replay (a peer restarting and replaying a frame from long ago) can only be fixed properly with persisted dedup state; today the time window is the backstop.

One further fact is relevant to this decision's reasoning but is not a residual risk: **`MessageRouter.MaxConnectionsPerPeer = 3` is currently an unused constant** — the only hit in the whole repository is its declaration at `MessageRouter.cs:27` (the other occurrence is in the `Agent.md` prose). In other words, "at most 3 connections per peer" does not hold today; this record's out-of-order argument does not depend on it.
