# 诊断 CI flake

只在任务是**排查一个既有的概率性测试或 CI 失败**时用本流程。保留请求的读 / 写范围——诊断**不**授权修改、workflow 重跑或 CI 配置变动。

## 把证据定下来

记下仓库、workflow、job、commit SHA、runner 标签、时间戳、精确失败测试或命令、首个稳定失败签名。把基础设施消息与测试输出分开。

对比多个失败与通过的运行。**优先**选同 SHA 的运行；当做不到时，先核实比较的 commit 之间相关测试与 CI 配置完全相同。**一次**通过的重跑不证明基础设施故障，**一次**超时也不证明生产代码有 race。

用 CI 平台的日志与元数据判断失败是否在同一台 host 或同一资源命名空间重叠。保留支撑运行的链接，不要粘贴大段日志。

## 分类失败

依据记录证据分类，不是依据最终修法：

- **主机资源争用**：同一端口、socket、数据库、可预期路径、缓存或外部命名空间被独立进程或 job 抢占。
- **生命周期没收口**：teardown 在子进程、worker、流、服务器或回调到达静默前返回；后续输出或突变进入另一个测试。
- **进程全局污染**：结果依赖测试顺序或漏出的 `process.env`、`cwd`、fake timer、全局、mock、locale、模块状态。
- **载量敏感的同步**：用 sleep、轮询间隔或"事件循环转一圈"代替真实就绪 / 完成信号。
- **平台 / 入口路径不匹配**：失败稳定地跟随某个 OS、shell、文件系统规则、源码 / 构建模式或可执行入口。Windows 与 POSIX 在时间戳精度、环境变量大小写、句柄释放时机、权限语义上的差异使"macOS 通过"对 Windows lane **没有任何**意义。
- **产品并发缺陷**：测试掌控自身资源、用显式重叠能确定性复现，并暴露了已发货行为里的 race。
- **外部 provider 瞬态**：失败由真实 API 或网络边界拥有，匹配它文档化的 retry 策略。
- **Runner 基础设施**：checkout、依赖下载、磁盘、主机进程、runner 服务在测试命令之外独立失败。这种归类要求直接的 runner 证据；当 self-hosted 池子没有暴露主机指标，如实说，靠日志里能看到的部分分类——一条签名在同池无关 branch 上重复出现，本身就是共享主机争用的证据。

证据支持多个独立事实时，**各自报告**。不要把"超时 + 信号 + 退出码 + 断言"塌缩成一句"猜到的结论"。

## 复现最小相关拓扑

从归属测试文件或聚焦测试名开始。只把并发**增加到**恰好复现该签名的第一个拓扑：

1. 一个测试进程；
2. 并发测试或文件；
3. 多个独立测试运行器进程；
4. 归属仓库的 gate 用它配置的 worker 数；
5. 共享同一被怀疑主机资源的独立 job / runner 进程。

匹配活动 runner 配置、环境旋钮、源码 / 构建模式与平台。不要降低生产超时或加随机负载只为造出一种"不同的失败"。

签名属于本地主机跑不到的平台时，阶梯停在最后能到达的一档。**记下**这层限制，不要用别处一次通过的结果来代替，然后用 CI 作为复现，逐 run 只改一个怀疑的拥有者，让结果可归属。

怀疑 race 时，把概率性的时序换成 contested transition 的 barrier。怀疑主机争用时，证明同一标识符被同时抢到，或证明原子唯一分配消除冲突。

## 在拥有者处修

实施已授权时，修**分配、发布就绪、突变全局状态、拥有 teardown** 的那一段组件。不要把失败藏在 snapshot normalizer、retry 包装、更宽的超时、全局串行设置、或更弱的断言里。

稳定的 fixture 数据与活的资源分配要分开。录好的 URL 仍是稳定的——fixture 把它的 transport 映射到 OS 分配的端口；稳定的期望路径可以仍是断言，但不该变成共享的可写目录。

## 收尾

证据齐全当且仅当：

- 原始签名有可支持的归类；
- 最小相关拓扑复现了它，或者外部证据充分且复现限制已显式说明；
- 已授权的修法在反例或修复前状态下失败、在同拓扑下修复后通过；
- 拥有者要求的并发进程、还原、或静默 teardown 证据通过；
- 残留的 CI 检查按真实观察状态报为通过 / pending / 跳过 / 失败。

不要反复跑直到"碰巧通过"然后把它叫稳定。选中的证据把结论立住就停；缺一个事实就报告，并标出它卡在哪一档。
