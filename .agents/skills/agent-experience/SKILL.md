name: agent-experience
description: 设计 agent 工具 / 技能 / 上下文加载或多步工作流时使用——让信息可被检索、让上下文高效被用。
---

设计 agent 用的接口时，把"可被发现 + 上下文高效"当成两条硬约束。本 skill 是**指导**，不是清单。

## 最小上下文起步

让最常见的入口路径**一开始**就能看见用途 + 可用动作 + 关键约束，再视任务复杂度加载详细指令。不要让 agent 必须先读完一份长 prompt 才能判断"这一步该不该走我这个接口"。

## 让检索显式

每一个**推迟**读的资源都要回答两个问题：

- 它**描述**什么——名字、用途、"被读到时属于什么状态"
- 怎么**取到**——给路径、id、API、检索方式

推迟不是删除；推迟是"先给指针，再用时再取"。

## 关键约束前置

权限、破坏性副作用、必须先验证的状态——都摆在执行**之前**，不放在执行**之后**的错误信息里。agent 在准备调一个工具时就该看见它能否调、是否需要确认、会有何后果。

## 偏好有界输出

返回结构化的结果 + 必要的取细节路径（id / 索引 / offset），而不是把整个日志 / 整个文档 dump 给模型。"先给摘要、需要时再放大"是节省上下文的正道。

## 用"局部性"

把**一份**操作所需的最可能邻近上下文**一起**返回。例如：返回一条消息 reply 时带上前几条消息；返回查询结果时带上总和与可见长度。**显式**标出省略 / 截断的位置，并给"取更多"的路径。

不要把"取更多"埋在不显眼的细节里——它必须是返回结构的一等字段。

## 评估总开销

节省上下文不是孤立指标。如果"少返回 N 个 token"导致模型多搜索 N 次 / 多读 N 个文件 / 多错 N 次，省的就全赔回去了。**端到端**算：返回字段、典型推理路径、典型错误率一起看。
