# Agent Note: 短 NodeId 前缀歧义被静默取第一个（`/msg` 与 `/file send` 的静默误投）

Status: implemented

## Problem

`P2PChatTui` 把 `/msg` 与 `/file send` 的 `<联系人|节点ID>` 参数拿到本地联系人表上解析 —— 先别名精确匹配，再按 NodeId 的 hex 前缀 —— 并且**取第一个命中**。两个不同的 NodeId 各为 20 字节，即 40 位等长 hex，因此互不为前缀：**完整**的 40 位 NodeId 至多命中一个联系人。歧义只可能由**更短**的输入产生，而一旦产生，解析是静默的 —— 没有拒绝、没有告警、没有日志，调用点上也**没有任何东西**能区分「唯一命中」与「撞车」。

伤害不等于「消息发错人了」。消息是用**错误**联系人的会话密钥加密并发给错误对端的，而对那个对端而言这条消息是**可读的** —— 密钥在它手里。真正的收件人根本没收到，而用户以为发出去了。**不能**由此推出的是明文上线：链路上的旁观者看到的仍然是用一把他不持有的会话密钥加密的密文。破掉的是**对被静默替换掉那个对端**的机密性，不是链路的保密性。

另有两个事实使它既难察觉也难复现：

- 本地回显行 `我 -> <别名>: <文本>` 在发送**之后**执行，且与发送成败无关，因此它不是信号。它以与一次正确发送完全相同的形状打印出被替换对端的别名，没有任何东西把它标成缺陷。
- 歧义面**随时间变大**。一次成功的 `/connect` 会自动把对端落盘进联系人表，别名形如 `peer-{hex[..8]}`，而那张联系人表正是本解析的输入集。每一次自动登记都在为短前缀增加一个可能撞车的条目。

## Decision

**唯一不变量：歧义必须拒发。** 解析落在 `Core.Extensions.ContactResolver`，作为唯一实现；TUI 只调用，不自己再写一份。先别名精确，再 NodeId 前缀：

- 别名**恰好命中一个**联系人即解析到它；
- 否则 NodeId 前缀必须**恰好命中一个**联系人；
- **命中多于一个即歧义，调用方不得发送。** 解析结果携带完整候选列表，`P2PChatTui.ReportContactLookupFailure` 拒绝发送、报出命中数、列出候选的短 ID / 别名 / 端点，并说明打更长的 NodeId 或用精确别名即可消除歧义。

两个不同的 NodeId 是等长 40 位 hex 且互不为前缀，因此**只有短于 40 位的输入才可能歧义** —— 恰好就是这条拒绝覆盖的集合。重复别名同样按歧义拒发：`/add` 不强制别名唯一，因此「几个联系人共用一个别名」是可达状态，替用户从里面挑一个是同一个缺陷。

别名排在前缀之前，是因为别名是用户自己起的名字，而短 hex 前缀是一个标识符的子串，那张由自动登记对端持续增长的表一直在延长这个标识符集合。

### 把排序定下来不是修法

`ContactService.GetAllContactsAsync` 先按在线状态、再按别名排序，别名那一段用的是默认字符串比较器。在那里补一个显式 comparer，是读完本文的人最可能顺手做的改动，而它不是修法：它让选择**可复现**而不是正确，而能够影响谁排在最前的一方照样拿到整条链。可复用的判据：

> **排序确定 ≠ 选中正确。**

这也是解析器对排序不作任何断言的原因：它唯一回答的问题是，这个输入在给定集合里是否指向**唯一**一个联系人。

### 解析为什么下沉到 Core

理由与 `EnvelopeCodec` / `EnvelopeVerifier` 落进 Core 的那一条相同，而且它是结构性的、不是风格问题。`P2PChatTui` 无法在进程内构造 —— 它依赖真实控制台状态 —— 且 **`tests/` 下没有任何项目引用 `P2PChat.UI`**。于是这段解析是一个既无行为测试、又在不新增程序集依赖的前提下无法补上测试的私有方法：在那个形态下，只有**刻意构造的歧义输入**才能暴露缺陷，而当时没有任何地方能构造它。逻辑是纯函数、不依赖 UI，把它放在能被引用的层，是唯一能给它装上测试的做法。

### 解析不证明什么

解析出某个联系人，**不**代表那就是要找的那个人。联系人表是本地存储，其完整性是另一个问题 —— `/add` 手输的条目，以及某次 `/connect` 的 TOFU 接受被自动落盘的条目。`ContactResolver` 只保证一件事：**在给定联系人里，该输入至多指向一个。** 面向用户的文案不得把它表述成身份验证。

## Alternatives considered

**给 `ContactService` 的排序补 `StringComparer.Ordinal`。** 否决：它让结果确定，而不是正确。缺陷在于「做了选择」这件事本身；稳定的排序照样做了选择，而能影响谁排在最前的人照样拿到结果。排序确定 ≠ 选中正确。

**加一个「前缀最少几位」阈值，短于该位数即拒发。** 否决：碰撞成本确实随前缀变短而陡降，但那是量级判断，没有实测依据；而写死一个位数会变成一条**看上去权威、实则随联系人表增长而悄然过期**的断言。它拿一条假精确的规则替代了真正的不变量，而且会连**本来毫无歧义**的输入也一起拒掉。

**保留取第一个，只在 UI 上提示。** 否决：提示不改变行为，而伤害发生在**任何提示能显示之前** —— 消息已经用被替换对端的密钥加密并发出去了。让发送以解析结果为条件，就是本决策的全部内容。

**给 UI 项目补一条测试 ProjectReference，就地覆盖那个私有方法。** 否决：它确实可行，换来的却是一条产品程序集依赖边，外加一个别扭的永久落位。收敛类决策的规则在这里同样适用：「一个消费者够不到共享实现」的正解是把实现搬走，而不是把依赖图拉宽。那条依赖边还会把逻辑留在其它任何调用方都够不到的地方。

**歧义时让用户从候选里挑，用户不选就默认取第一个。** 否决：它让「挑一个」重新成为可达结局。拒绝是唯一无法被疏忽、误点、或者「赶紧发了算了」的压力推到的状态。

## Consequences

- 打出有歧义的短前缀时，用户**被拒绝并看到候选列表**。这是有意的行为变化：原先会发给某个任意联系人的输入，现在什么都不发。多打几位、打完整 40 位 NodeId、或用精确别名都能消除歧义。
- **代价：歧义输入是硬失败，没有自动兜底。** 刻意不做「你是不是想找」的选择器，因此认不出候选的用户必须自己去查 ID。
- **`ContactService` 的排序 comparer 刻意不动。** 排序仍然决定联系人表和候选展示的显示顺序，那是呈现层面的事；它已经不再对「哪条消息归哪个联系人收」有任何发言权。改它不会改变发送行为，而将来若有人改它，**不得**被描述成本决策的修法。
- **这段逻辑第一次可被单测覆盖。** 解析落进 Core 之后，它的不变量是被直接断言的，而不是从一个无法构造的 UI 上反推出来的。
- **展示的候选列表有上限**：最多 8 条，其余以计数报出，这样大碰撞集仍然可读；解析器返回的仍是完整集合。

## Testing

`tests/P2PChat.Core.Tests/ContactResolverTests.cs` —— 12 条。变异验证：把前缀分支改回「取第一个」，**恰好 3 条**变红，而这份集合本身就是重点：

- `短前缀_命中多个联系人时判为歧义_且不返回任何一个` —— 两个联系人共享 4 位前缀；
- `短前缀_命中三个联系人时同样判为歧义` —— 同样情形下三个候选，同时钉住候选列表是完整返回的；
- `歧义时即使其中一条恰好排在前面的联系人存在_也绝不选它` —— 专为「用排序来修」这个假修法设的陷阱：排在最前的那位**确实存在**，而且仍然不被选中。

第三条正是该文件类注释说「本文件不对排序作任何断言」时的意思。少了它，一个「歧义时取列表里恰好排最前的那个」的实现，能通过只检查两候选情形的测试集。

其余用例覆盖这条拒绝不应破坏的东西：唯一别名、别名忽略大小写、完整 40 位 NodeId、重复别名按同样方式拒发、别名优先于同样能命中的前缀、零候选与空列表都报「未找到」而非「有歧义」（UI 对这两种措辞不同）、对 null 集合或 null 目标抛 `ArgumentNullException`，以及「不重排调用方集合」这一纯函数契约。

## Deferred

- **歧义面随联系人表增长而变大**，本决策不缩小它。混合网络、或一组协助节点自动登记更多对端，都会增加短前缀可能撞上的条目数。拒绝在表变大时依然正确；未解决的是**任何能缩小这个面的东西**。
- **`ContactService` 的排序 comparer 就这么留着，是刻意的。** 它决定 UI 列出什么；它绝不能变成「决定哪条消息归谁收」的那一环，而在那里补 comparer 也不是本决策的修法。
- **联系人表自身的完整性未被触碰**：`/add` 手输的条目、以及某次 `/connect` 的 TOFU 接受被落盘的条目，仍是本地存储里是什么就是什么。解析不是验证。
- **`P2PChatTui` 仍然没有测试项目引用**，因此 UI 上的拒绝路径与候选展示没有单测覆盖；本决策陈述的每一条规则都由 `ContactResolverTests` 覆盖。`scripts/e2e-verify.ps1` 通过给每轮运行换一个独立别名来绕开别名撞车，因此端到端脚本同样不覆盖歧义路径。
- **e2e 脚本里那条绕行注释本身**，仍把别名撞车的解析描述成一个开放缺陷，并让读者去翻一份交接文档看细节。那句措辞已经过期；更新它属于脚本，不属于本 Note。
