# Agent Note: 自动密钥交换的响应曾经完全不验签（首条 `/msg` 上的静默会话密钥替换）

Status: implemented

## Problem

当用户给自己尚无会话密钥的对端发第一条 `/msg` 时，走的就是 `ChatService.ReadKeyExchangeResponseAsync` —— 该对端由 DHT 自动发现或 `/add` 得到，而不是用户刚刚用 `/connect` 亲手连上的。`EnsureSessionKeyAsync` 直接进入 `PerformKeyExchangeAsync`：把 `KeyExchangeMessage` 写进一条出站连接，再从**同一条连接**上读回应答。

那条路径的准入逻辑是 `MessageRouter.DeserializeEnvelope` 加载荷反序列化，随后把 `response.EphemeralPublicKey` 直接送进 ECDH。没有验签、没有身份核对、没有新鲜度检查，**没有任何准入步骤**：**会话密钥单方面由应答方决定。**

后果是静默的，而不是吵闹的：

1. **任何能应答该端点的主机都可以指定自己的临时公钥。** 它给出自己控制的公钥，ECDH 与之完成，派生结果就成了这个会话的密钥。
2. **密钥被记在预期对端的 NodeId 名下。** `SetSessionKey(recipient.NodeId, sessionKey)` 用的是本机解析出的 NodeId，**从不是应答方的**。会话看着健康、日志写着密钥交换完成、对话照常收发 —— 只是其中每一条私聊都被应答方读得明明白白。
3. **可观测行为里没有任何东西能区分这两种情况。** 没有拒绝、没有告警、没有第二条日志：缺陷与合法交换产生同一个观察结果 —— 这正是它能长期待在本应用主路径上不被发现的原因。

同一路径上还占着第二个缺陷。该方法直接消费连接上的字节流，走不到 `MessageRouter.RouteIncomingAsync`，因此每一条正常入站帧都会经过的重放防护在这里也不执行。后果不只是「少了一道检查」，而是**归属不一致**：同一个协议存在两套防护强度，取决于恰好是哪个读取方在消费那份响应。

## Decision

密钥交换响应的准入是**四道判据的串联，全部在写入会话密钥之前强制执行**，都在 `ReadKeyExchangeResponseAsync` 内：

- **判据 ①：回显每次交换一次性的 `ConversationId`。** 请求携带 `kx-{Guid.NewGuid():N}`，响应必须原样返回（`StringComparison.Ordinal`）。它替换掉的关联值原本是恒定的 `recipient.NodeId.ToHexString()`；**值恒定则回显校验形同虚设，所以值与检查必须一起改**。合规对端本来就会回显 —— `KeyExchangeHandler` 写的是 `ConversationId = message.ConversationId` —— 因此判据 ① 不会误杀。
- **判据 ②：ECDSA 验签**，走 `Core.Extensions.EnvelopeVerifier.Verify`，即与 `/connect` 路径共用的那一份唯一实现；它本身已强制 `NodeId.FromPublicKey(公钥) == SenderId`。
- **判据 ③：签名者必须是预期对端。** `NodeId.FromPublicKey(envelope.SenderPublicKey!)` 必须等于 `expectedPeerId` —— 它来自 `FindNodeAsync` 或联系人记录。身份由公钥派生，**绝不取自载荷里的 `SenderId`**。
- **判据 ④：`IReplayGuard.TryAccept`**，与每一条正常入站帧相同的那道准入。

任一判据失败即抛 `KeyExchangeRejectedException`（`src/P2PChat.Core/Models/`）并记 `LogError`。用 `Debug` 是错的等级：要消除的恰恰是**什么都不报**的那种结局。

`ChatService` 的构造函数把 `IReplayGuard` 设为**必填**形参：不带默认值，且对 `null` 抛 `ArgumentNullException`。可选形参会让「忘记注入」等价于「密钥交换无防护」，从而静默复现本决策要消除的那条不一致；每个构造点（DI 装配、测试装配）随之同步更新。

不是 `KeyExchangeMessage { IsResponse: true }` 的帧（包括对端在同一连接上主动发来的密钥交换**请求**）仍然交回 `RouteIncomingAsync`，读取循环继续。于是一条连接可以在握手未完成期间照常承载正常入站流量。

### 为什么判据 ③ 在这里是真正的拒绝，在 `/connect` 那里不是

`/connect <ip:port>` 连的是**未知端点**：用户给出的就是地址，其目的正是去问「那边是谁」，所以它能拿出的最强判据只能是 TOFU 加端点连续性 —— 而自签的陌生主机与合法节点在密码学上不可区分。这里的预期身份**事先已知** —— 就是本机正要寻址的那个 NodeId。持有完全合法密钥对的攻击者，其响应能完整通过 ① 与 ②，认出它的只有 ③。

这就是两条路径的判据不能互相顶替的原因，也是两个拒绝异常类型不共用的原因。

### `KeyExchangeRejectedException` 刻意是独立类型

`P2PChatTui` 内部的 `HelloRejectedException` 覆盖 `/connect` 命令 —— 作用域限于那一条命令的局部失败，对用户的含义是「连不上」。本异常位于 `ChatService.SendPrivateMessageAsync`，即用户发一条 `/msg` 必经的主链路，含义是「消息没有发出去」。两者需要不同措辞，因此类型分开。

本类型携带一条 UI 依赖的语义约定：**抛出它就意味着会话密钥一定没有写入、明文一定没有上线。** 任何发生在写会话密钥**之后**的失败都不得使用它 —— 否则把本类型读作「可以安全重试」的调用方会被告知一件不成立的事。

### 判据 ① 无状态，是必需的

`IReplayGuard` 是本地状态，替代不了判据 ①。攻击者为某个受害者录下的响应带着一条该受害节点从未见过、也不在去重缓存里的 `MessageId`，防护会放行。判据 ① 比对的是本次交换刚生成的一次性值，不依赖任何历史才有意义。这与 `/connect` 路径上回显校验独立存在的理由完全相同，在这里同样成立。

## The class, not the instance

`HANDOFF.md` §8 第 5 条早已记下：这一类缺陷是**一族**，不是一串互不相干的 bug。`GroupChatService.ReadPeerPublicKeyFromResponseAsync` 形状完全相同 —— 它同样在自己持有的连接上读密钥交换响应 —— 而它**已经**做了验签与「应答方是否预期成员」的核对。**正确的模式在本仓库是已知的，只是没有被一致地应用**，这是「按已报出的点修补会留下错误印象」的最强证据：只修一个读取方之后，「密钥交换响应现在被验证了」会被读成**协议**的性质而不是某个方法的性质，而只有每个读取方各自强制时它才成立。

同一次排查还给出两条判断规则：

- **严重度看影响上限，不看放大器的响度。** 这处缺口在仓库自己的清单里被记为影响较低，理由是它缺少 `/connect` 路径所具备的放大器（主动去连一个陌生主机）。两者的影响上限完全相同 —— 该会话机密性的彻底丧失 —— 且它就落在主功能真正会走的路径上。
- **「它绕开了共享守卫」是发现，不是小毛病。** 直接读连接字节流的路径，**一点都继承不到** `MessageRouter` 的防护；而防护缺失在这里**永远不会显式失败**：缺一道守卫产生的是一个能正常工作的系统，而不是一个错误。因此「同一个协议的两个读取方带着不同防护强度」是要**去搜**的东西，不是顺带记一笔的东西。

## Alternatives considered

**依赖 ECDH 握手本身（响应已经证明了所需的一切）。** 否决：ECDH 证明的是双方都参与了一个共享秘密，它对**对方是谁**只字未提。换成应答方自己的临时公钥，得到的仍是一个完全有效的共享秘密 —— 密钥协商是真的，对端不是。

**验签，并只用已验签信封里的身份。** 否决：验签确立的是「信封与它携带的那把公钥自洽」，而不是「这把公钥属于本会话要联系的那个节点」。持有合法密钥对的攻击者能完整通过这一项；它比什么都不做强，仅仅因为它排除了伪造与篡改。

**保留恒定的会话键作为关联值，并在外面加回显校验。** 否决：值恒定时应答方每次都会回显它，包括重放一条从别的交换录下的响应时。检查会**看上去**是一条判据，实际上一条都挡不住 —— 比不写还糟，因为那份判据清单会被人当作它并不提供的保证引用。

**拿载荷里的 `SenderId` 去比对预期对端，而不是从公钥派生身份。** 否决：载荷完全由对端可控；且这一族缺陷的历史里已经出现过「一个方法取信封、它的调用方取载荷、相距六行」的实例。只有从已验签公钥派生，才是验签结果真正支持的形式。

**把响应像其它入站帧那样交给 `RouteIncomingAsync` 路由。** 否决：该响应是本进程自己发起、在同步等待中的握手续接，不是入站分发。路由它等于把一条密钥交换响应交给为聊天流量准备的 handler，并把控制权交还给一个仍需要结果的握手。这条路径保留自己的判据；需要纠正的是**它必须带上同样的判据**。

**接住拒绝、不带会话密钥继续。** 否决：那等于在没有密钥的情况下把明文推上线，而一边告诉用户发送失败一边照发，正是本决策要消除的失败模式。

**少一道判据 —— 去掉 ④，保留 ①②③。** 否决，但理由比第一眼看上去弱：判据 ① 已经挡住了「录下响应重放」，因为每次新交换都带一个录下的响应不可能带上的新鲜关联值。判据 ④ 补上的是让这条路径与其它每一条入站帧**同强度**，而不是一份手工挑出来的子集；它还覆盖「本机已接受过的信封标识在关联值仍然新鲜的情况下再次投递」。既定目标是消除两套强度的不一致，而只有两个读取方都过同一道守卫，这个目标才成立。

## Consequences

- 给新对端发第一条 `/msg` 变成「**先验后信**」：响应必须回显本次关联标识、通过 `EnvelopeVerifier.Verify`、由预期对端的密钥签名、并通过重放守卫，会话密钥才存在。每条拒绝路径上都不写会话密钥、不把明文推上线。
- **代价：端点不对的对端现在会让发送失败，而不是静默接受一把密钥。** 若发现层返回的端点属于一个并非预期节点的主机，用户得到的是一条点名预期与实际短 ID 的错误，而不是一个悄悄能用、悄悄在泄漏的会话。这是**正确**的结局，而对曾经拥有这种对端的人，它表现为「以前能发」。
- **这条路径强于 `/connect`，两者不可当作同一个机制读。** `/connect` 在首次接触时无法拒掉自签的陌生主机；这里的判据 ③ 之所以是真正的身份检查，是因为预期身份事先已知。日后若要把两者统一，必须**保住**这个差异，而不是把它压平成两者中较弱的那个。
- **这条路径上的关联值是每次交换的 nonce。** 任何在 `ChatService` 路径上读 / 匹配 `KeyExchangeMessage.ConversationId` 的代码，必须把它当成生命周期为单次握手的**不透明 nonce**，而不是会话键 —— 私聊的会话键是 `ConversationId.ForPrivate(...)`，是另一个值、另一种生命周期。
- **`IReplayGuard` 作为必填形参，对每个构造点都是破坏性变更**，且是刻意的：漏注入必须在构造时响亮地失败，而不是退化成「握手无防护」。
- **三条结构守卫断言的是源码文本** —— 是否调用了 `EnvelopeVerifier.Verify`、是否调用了 `_replayGuard.TryAccept`、以及去注释后的源码里不出现 `new NodeId(response.SenderId`。一次把调用挪过行的排版性重构就会让它们变红。取舍是「宁可假红也不放过检查被整段删掉」；维护者看到它们红，应当首先怀疑某个调用被挪动或重排了。

## Testing

`tests/P2PChat.Chat.Tests/KeyExchangeResponseVerificationTests.cs` —— 11 条。`ChatService` 可以在进程内真实构造，因此这些是跑**真实密码学 + 真实 `IReplayGuard`** 的行为测试：断言的是「到底写了什么、到底上线了什么」，而不是源码里写了什么。

- 判据 ② 与冒名形态：`密钥交换应答未签名时拒绝发送_不写会话密钥也不把明文推上线`，以及 `密钥交换应答的签名与公钥不自洽时拒绝发送` —— 一把合法 P-256 公钥装在 `SenderId` 声称是另一个节点的信封里、用攻击者自己的私钥签出；只要身份是从载荷里读的，这一招就绕得过验签。
- 判据 ③，也就是 `/connect` 路径没有的那一条：`密钥交换应答由非预期节点签名时拒绝发送_即使那条签名完全有效`，外加 `攻击者的临时公钥不得被用来派生会话密钥`。后者单列是有意的 —— 它断言攻击者那条临时公钥**确实是可解密的**（否则前一条可能只是因为攻击者恰好造了把坏公钥而通过），且在预期对端名下**一个字节的会话密钥都没写**。
- 判据 ①：`密钥交换应答回显的不是本次关联标识时拒绝发送`，以及 `关联标识每次交换都必须重新生成_不得退回恒定的会话键`。后者跑两次交换并断言两个关联值不同 —— 这才把「恒定值」钉成回归项，而不是留给评审去发现。
- 判据 ④：`同一条密钥交换应答重复投递时第二次被重放防护拒绝` 重投一条签名正确、回显正确、且由预期对端签名的响应，关联值是最新的但 `MessageId` 已被接受过 —— 前三道判据两次都会放行，只有守卫能拒掉第二次。
- 针对「一律拒绝」这种改法：`四道判据全部通过时正常建立会话并发出消息` 断言 32 字节会话密钥与非空的 `TextMessage.Content`。
- 结构守卫 K1–K3：`ChatService必须调用Core的EnvelopeVerifier验签`、`ChatService的密钥交换应答必须经过重放防护`、`ChatService不得用载荷里的SenderId判定对端身份`。这三条补的是负向用例补不了的缺口：上面每一条都是负向断言，所以一旦有人把校验软化成「告警后继续」，它们**照样全红**，但**正向接线被整个漏掉**没有任何东西会发现。K3 读的是未去注释的原始文本，因为它要防的既是不当的写法，也是不当的注释。

命名惯例与 `/connect` 那条路径的守卫一致：用例的**名字就是问题描述**，因此那份清单读起来就是一份「绝不能再回来」的清单。

## Deferred

- **四道判据不证明什么。** 它们确立的是：响应由「本机本打算寻址的那个身份」之私钥持有者签发，且它回答的是本次交换。它们**不**确立对端机器没有被攻陷，也**不**确立 `FindNodeAsync` 返回的那个端点属于该节点 —— 冒名端点仍然无法以预期 NodeId 应答，但「这个端点就是那个节点」属于**发现层的信任问题**，至今未决。面向用户的文案不得把它表述成「对端已验证」。
- **`GroupChatService` 的探测路径**（`ReadPeerPublicKeyFromResponseAsync`）形状相同。它验签、也核对应答方是否为预期成员，因此保护会话密钥的那两道判据都在；它没有回显判据、也没有调 `IReplayGuard`，且它的 `ConversationId` 就是成员的 NodeId。它派生的是用于包装群密钥的长期公钥，而不是私聊会话密钥 —— 这份残余的不对称尚未解决。
- **清单条目已过期。** `Agent.md`（`ChatService` 方法表里 `ReadKeyExchangeResponseAsync` 那一行，以及把它描述成绕过验签与重放防护的残余风险那一行）仍在描述旧契约。两行都需要与本决策同一次提交的更新；该文件不在决策记录树内。
- **自动密钥交换路径没有端到端断言。** `scripts/e2e-verify.ps1` 的 Phase 2 覆盖 `/msg` 往返，`/connect` 往返同样没有断言。
- 结构守卫对排版性重构的敏感性记在 `## Consequences` 下。
