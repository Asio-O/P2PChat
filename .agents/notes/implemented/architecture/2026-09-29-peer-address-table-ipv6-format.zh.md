# Agent Note: 对端地址表把地址字段宽度硬编码为 4 字节，因此 IPv6 条目以第二个字段承载

Status: implemented

## Problem

`get_peers` 应答里的 `p2pc_peers` 字段是一个 bencode 列表，条目固定 26 字节：`[20B NodeId][4B IPv4][2B Port BE]`。地址字段的宽度被硬编码为 4。

`IPAddress.GetAddressBytes()` 对 IPv6 地址返回 16 字节，于是那条路径上固定 4 字节宽的 `Buffer.BlockCopy` 读走了地址的前四个字节，并把它们当作一个 IPv4 地址来解释。`2001:db8::1` 变成了 `32.1.13.184` —— 一个语法合法、却属于完全不同主机的地址。没有异常抛出，没有日志记录，也没有降级分支：地址表开始播报一个并不属于该对端的地址，而下游**无从察觉**。

**这条路径当前不可达，而这正是值得写下来的部分。** `UdpTransport` 绑定 `AddressFamily.InterNetwork`，因此今天 IPv6 地址进不了这张表。所以可复用的判据不是「这个缺陷无害」，而是它的反面：

> 一条当前走不到的路径，不等于一条安全的路径。它只是还没被走到过。

截断发生在编码器里，所以它会在传输层一接受 IPv6 时**自行激活** —— DHT 层不需要任何改动去宣告它，而现有每一行日志都仍然在报「成功」。

同一区域的解析器上还坐着第二个缺陷。

`FlattenByteList(list, entrySize)` 收下 `entrySize` 形参，却无条件调用按 26 字节切分的解析器：**形参在签名里，行为里没有。** 于是任何按别的条目宽度调用它的代码，拿到的仍然是 26 字节切分，标准 6 字节的 `values` 列表因此被切成错位条目。

它长期没暴露，是因为 `values` 那条路径的产物无论如何都会被下游丢弃 —— 标准 `values` 条目不带 NodeId，因此过不了「条目 NodeId 必须等于查询目标」那一关。**被掩盖的错位解析仍然是错位解析。** 形参承诺了、函数体没有兑现的东西，距离给任何**确实**带着 NodeId 可供匹配的调用方产出错条目，只差一次改动。

## Decision

**两个字段并存。** `p2pc_peers` 保持 26 字节 IPv4 布局，**逐字节不变**；另加 `p2pc_peers6` 承载 IPv6，每条 38 字节：`[20B NodeId][16B IPv6][2B Port BE]`。`get_peers` 应答按地址族把缓存条目分流到两个字段，且每个字段只在至少有一条目时才写出。

**这个形状由项目 Lead 裁决，不是用户的选择，且可以推翻。** 底层问题已经问过用户两轮未获答复。本仓库自己的纪律在此适用：未获答复的轮数本身就是信号，不修饰；而第三次问同一个问题不会产生新信息。因此本决策依据的是 Lead 的裁决，而不是一条已陈述的用户偏好。将来回看它的人应当把「双字段」读作一个带理由的提案，而不是用户提出的需求。

随格式一起落地三条性质：

- **编码按地址族选布局，遇到未知族抛异常。** `Bencode.SerializeCompactPeer` 从 `AddressFamily` 推导地址字段宽度，遇到不认识的族抛 `ArgumentException`。无法编码某条目时调用方跳过它，并打一条指明对端与端点的告警 —— 于是「无法编码的地址」留下痕迹，而不是留下一个错误地址。这个选择是刻意的：宁可在这里失败，也不要发出一个不属于该对端的地址。
- **解析按宽度分派，遇到未知宽度抛异常而不是猜。** `FlattenByteList` 对 `entrySize` 做 switch —— 26 走 IPv4 解析器，38 走 IPv6 解析器，其余抛出一条同时写明两个已知宽度的 `ArgumentException`。标准 6 字节的 `values` 列表移进自己的方法 `FlattenValuesList`：它的字段布局在**种类**上就不一样，不只是宽度不同，两者不再共用同一个函数。共用一个函数，正是当初那个被忽略形参的来源。
- **解析出的条目上，NodeId 改为可空，命中判定处显式跳过 `null`。** 标准 `values` 条目没有属于自己的 NodeId，而代码在那条情况下确实持有的那个 NodeId 属于**响应者**，不属于该条目。因此 `FindNodeAsync` 的命中判定显式丢弃 `null`，而不是把「缺失的 id」当成身份。

## Alternatives considered

**给现有 26 字节条目加一个宽度标记位**（首字节标识条目布局）。否决，决定性的理由是**老节点的失败模式**。不认识某个宽度的节点不会停下来 —— 它按 26 字节切分，因为它的解析器就是这么写的，于是把新布局解释成**错条目**。而双字段设计让老节点**看不见地**失败：在字典里找不到 `p2pc_peers6`，它退回 `values` 且什么也拿不到，这是干净降级。**误解析远比缺失危险**，而本仓库已经为此付过两次代价 —— [消息签名](../bug-fix/2026-09-21-message-signing.md) 之后的 `EnvelopeCodec` 漂移事故，以及 `HANDOFF` §8.1.2 里那次假绿灯：一个数字被当成权威，而它所描述的东西根本没有被验证过。参见 [信封线路编解码收敛到 Core 的唯一真相源](../bug-fix/2026-09-28-envelope-codec-single-source.md)。

**接受不兼容，另开协议版本。** 就正确性而言这是最干净的选项：没有双布局，没有可能被读者漏掉的字段，处处一种格式。它输在**迁移成本** —— 过渡期需要两套网络与两套运维，而这套协议的实际部署规模很小、节点又是手工更新的。它不算错；它是在另一种规模下的正确答案。

**原地把 26 字节条目改成 38 字节**，不加新字段。否决：它直接破坏全部既有节点，且不留任何向后兼容路径。旧字段就是兼容面，把它覆盖掉，恰好毁掉了双字段设计之所以廉价的那个性质。

## Consequences

- **老节点是「看不见」地降级，而不是「看错」。** 找不到 `p2pc_peers6` 意味着退回 `values` 且从该字段拿不到任何条目。这是双字段形状的决定性理由，而且是设计的性质、不是迁移的偶然。
- **`p2pc_peers` 在字节级不变，因此本次改动不需要任何向后兼容处理，也没有改写任何既有测试的期望字节。** 一个在兼容处理上零成本的格式变更，正是「保住旧字段」而不是「另开版本绕开它」的实际理由。
- **一条 `get_peers` 应答现在可能带两个对端列表字段**，读取方必须处理「只有前者 / 两者都有 / 两者都无」三种字典形态。
- **代价：协议多一个 key。** 每个写应答的节点必须保持两个字段一致，每个读取方都必须两个都试。
- **未知地址族分支是刻意吵闹的。** 它把原本「静默产出错误地址」变成一次异常加一条指明受影响条目的告警。

## Deferred

- **IPv6 传输层本身还不存在，因此没有数据源。** 在它落地之前，`p2pc_peers6` 永远不会非空。**所以本次改动完全不产生行为变化**：它既**不修复** `## Problem` 里描述的截断缺陷（那条路径依然打不到），也**不引入**任何新行为。它所做的，是把格式能力先备好，并消除一条**会在 IPv6 传输层落地时自行激活**的静默错误路径。它**不是** IPv6 支持，本 Note 中任何表述都不得被读成这一点。
- **混合网络下的条目取舍仍未定。** 同一个 `info_hash` 下既有 IPv4 又有 IPv6 对端时，两个字段都发、还是由响应方按请求方能力挑选？这**没有替用户选**，留作待定。
- **未知地址族分支在当前 .NET 上无法被测试触达。** `IPAddress` 只支持两个地址族，构造不出第三个族。**不声称**该分支被覆盖。
- **`get_peers` 应答里按地址族分流那段逻辑没有直接的单元测试。** 它位于一个大方法内部。被覆盖的是它调用的编解码层，而不是分流本身。
- [公共 DHT 无法发现对端节点](../bug-fix/2026-09-20-public-dht-peer-discovery-gap.md) 里记录的 26 字节 `p2pc_peers` 定义仍然准确、未被取代。该 Note 尚未提到这个兄弟字段，因此本 Note 是对它的**部分扩展**而非替换。
